# v12.14 — Recurrent rollout for 300+ chunk trajectories

**Status**: design (not implemented). Date: 2026-05-03.

## Problem

Current verl 0.4 path stitches a whole video trajectory into ONE training
sample:

```
training input = [system + user_q +
                  user_block_0 + asst_0 +    ← chunk 0
                  user_block_1 + asst_1 +    ← chunk 1
                  ...
                  user_block_N + asst_N]     ← chunk N
attention      = causal (full lower triangle)
```

Per-chunk independent rollout (the actual inference workflow) is correct;
the **training-side stitch** is the problem. Two consequences for 300+
chunk videos:

1. **Token capacity ceiling**: a 300-chunk trajectory ≈ 50K stitched
   tokens. `max_response_length` and `ppo_max_token_len_per_gpu` either
   truncate the tail (lose late questions' supervision) or OOM the actor
   forward (FSDP-sharded Qwen3-VL-8B + 50K seq + multi-modal exceeds 96GB).

2. **Train/eval distribution drift**: at training time `asst_N` can attend
   to `user_block_0..N-1`, including raw frames the model never sees at
   rollout time (rollout's chunk-N prompt only contains the current
   sliding window). `use_remove_padding + use_fused_kernels + flash_attn_varlen`
   (already enabled) un-pads but does NOT block-diagonalise across chunk
   boundaries — it cuts padding waste, not the cross-chunk visibility.

## Why P1.5 / D2 are NOT the right fix

- **P1.5 (custom reward_manager for per-chunk reward broadcast)**: solves
  reward attribution but doesn't reduce per-sample sequence length, and
  needs simultaneous changes to reward_loop, advantage, actor — large
  framework surgery for low-confidence dense gold.
- **D2 (block-diagonal attention via FA3 / Triton kernel)**: solves
  train/eval drift but still keeps the 50K stitched sample. Token capacity
  ceiling unchanged. Big kernel investment for half the problem.

## What MemAgent / ReMemR1 actually do

Both reframe the problem as **recurrent multi-action workflow**:

```
trajectory = [s1]                                # 1 input sample
            ↓ rollout (independent per chunk)
gen_batch_output = [s1_chunk_0, s1_chunk_1, ..., s1_chunk_N, s1_final]
                    ↑ N+1 INDEPENDENT training samples
                    ↑ each carries its own (prompt, response) — short, ~2-8K each
                    ↑ NO stitching, NO cross-chunk attention

sample_index = [0, 0, 0, ..., 0]                 # all map back to s1
final_mask   = [F, F, F, ..., T]                 # last one is the terminal action
```

Reward + advantage:

```
final_reward = compute_score(s1_final)            # outcome only
token_level_scores[sample_index] = final_reward   # broadcast back to every action
GRPO baseline computed over original `uid` (not action), then
advantage_scalar[sample_index] used to fill action's response tokens.
```

**Net effect**:
- Each action is a normal-length sample → fits in any reasonable
  `ppo_max_token_len_per_gpu` (4K-8K).
- Per-action attention is naturally block-diagonal (no kernel needed).
- 300 chunk × 8K = 2.4M total tokens, but spread across 300 micro-batches
  → never an OOM event.
- Training-time prompt for chunk N is byte-identical to rollout-time prompt
  (no cross-chunk leakage).

### Step 2 — Implement `StreamingVideoAgent` (~2 days)

Mirror `streaming_agent_loop.py:run()` but produce **per-action AsyncOutput**:

```python
class StreamingVideoAgent(Agent):
    async def rollout(self, batch: DataProto) -> AsyncOutput:
        actions = []                           # list of (prompt, response, ...)
        state = VideoTrajectoryState(...)
        chunk_idx = 0
        while chunk_idx < n_chunks and not done:
            chunk_prompt = build_chunk_prompt(state, chunk_idx)  # short, ~2-8K
            response = await self.chat.generate(chunk_prompt, ...)
            actions.append((chunk_prompt, response))             # independent sample
            state.update(response)
            chunk_idx += 1
        # Final aggregation action: gather all per-chunk answers
        final_action = build_final_summary_action(actions, state)
        actions.append(final_action)

        return AsyncOutput(
            batch={
                "prompts": [a.prompt for a in actions],
                "responses": [a.response for a in actions],
                ...
            },
            sample_index=torch.zeros(len(actions), dtype=torch.long),  # all → input s1
            final_mask=torch.tensor([False] * (len(actions)-1) + [True]),
        )
```

D1 chunk-internal recall multi-turn slots in cleanly: the `while` loop
becomes nested (inner = recall multi-turn within chunk → 1 action per
chunk; outer = chunk advance). Each recall round is its OWN action with
its own (prompt, response).

### Step 3 — Add recurrent path to ray_trainer (~1 day)

### Step 4 — Reward + advantage adaptation (~1 day)

**v12.14 first version: outcome-only broadcast (matches ReMemR1)**.
This is the ONLY safe baseline:
- `compute_score` sees the FINAL action's response (which contains all
  per-Q answers because the streaming agent emits them along the way)
- `final_reward` (the trajectory-level α-mix scalar already produced by
  `recipe_thinkstream/thinkstream.py:614`) is broadcast to all of
  the trajectory's actions via `sample_index`. Same as ReMemR1's
  `/tmp/refs/ReMemR1/verl/trainer/ppo/ray_trainer.py:1278-1303`.
- GRPO baseline grouped by trajectory `uid` (NOT per-action), then
  `advantage_scalar[sample_index]` fills each action's response tokens.

**Per-action / per-Q advantage** (e.g. "broadcast Q-i's outcome only
to the action that emitted Q-i's `<answer>`") is a SEPARATE algorithm
contribution, not a cheap adaptation. ReMemR1's recurrent path doesn't
do this — it does outcome broadcast + a small action-level reward
heuristic. `chunk_video_indices` makes the routing data available, but
turning it on changes the GRPO baseline definition (per-Q-action
groups vs per-trajectory groups) and needs its own ablation. Park this
as v12.15+.

### Step 5 — Config + smoke (~1 day)

```yaml
recurrent:
  enable: memory                          # off=legacy stitched, memory=recurrent
  chunk_size: 3000                        # max prompt tokens per action
  max_actions_per_trajectory: 600         # IMPORTANT: actions, NOT chunks.
                                          # D1 chunk-internal recall produces
                                          # 2 actions per recall'd chunk, so
                                          # max_actions = max_chunks × 1.5-2×
                                          # for safety. 600 covers a
                                          # 360-chunk trajectory with avg
                                          # 1.66 actions/chunk.

actor_rollout_ref:
  rollout:
    response_length: 4096           # PER-ACTION, not stitched total
    prompt_length: 8192             # PER-ACTION
  actor:
    ppo_max_token_len_per_gpu: 12288  # one action fits per micro-batch
                                      # (= prompt 8K + response 4K + headroom)
    use_dynamic_bsz: True
```

Smoke: pick a trajectory with ~300 chunks (catalog 240-360s tier) and
verify
- no truncation (n_actions reaches expected count, no `:1140`/`:1348` break)
- no `max_token_len assert` (each action ≤ ppo_max_token_len_per_gpu)
- no OOM (per-sample 12K, total tokens spread across actions)
- final_reward correctly broadcasts via sample_index
- GRPO baseline uses trajectory `uid`, NOT per-action uid

**Capacity unit reminder**: throughout this design `max_actions_per_trajectory`
is in ACTIONS, not chunks/turns. With D1 a single video chunk can produce
1 action (silent/answer/compress) or 2 actions (recall multi-turn:
turn1=tool_call, turn2=answer). Plan budgets accordingly.

`verl/verl/experimental/agent_loop/agent_loop.py:722, 938`), so
v12.14 must also extend:

  - `AsyncOutput`: add `multi_modal_data` field per conversation
  - `concat_output`: stitch per-action mm tensors + their metadata into
    the batched DataProto (preserve frames/video_metadata.frames_indices
    so historical-time MROPE survives the per-action split)
  - tokenization path: each action's prompt/response must run through
    `process_vision_info` exactly once (deduped across recall multi-turn
    rounds within an action)

Without these the recurrent path will silently lose visual context —
each action's text stays correct but the actor sees no frames.

## What stays / what changes

| Component | Stitched (current) | Recurrent (v12.14) |
|---|---|---|
| Per-chunk independent rollout | ✓ | ✓ same |
| visual sliding window + memory | ✓ | ✓ same |
| compress trigger + threshold | ✓ | ✓ same |
| D1 chunk-internal recall | ✓ | ✓ each recall round = its own action |
| Per-chunk frame_paths + MROPE | ✓ | ✓ same |
| **Training sample shape** | 1 stitched 50K-token sequence | N short ~5K-token sequences |
| **Attention** | causal full | per-action self-attention only |
| **Reward** | trajectory scalar at last token | scalar at final action's last token, broadcast via sample_index |
| **Advantage** | uniform over response_mask | uniform per-action over that action's mask |
| **OOM ceiling** | ~120 chunks (32K stitched) | ~indefinite (per-sample bounded) |
| **Train/eval drift** | cross-chunk attention leakage | none — per-action prompt = rollout prompt |

## When to actually do this

**Trigger conditions** (do v12.14 when ANY one fires). OOM is just one
of several failure modes — others fire EARLIER:

1. **Tail truncation in stitched response**:
   `streaming_agent_loop.py:1140` (chunk-prompt budget guard) or
   `:1348` (stitched response_length cap) breaks the outer loop before
   `chunk_idx == n_chunks`, silently dropping the late questions'
   gold supervision.
2. **`max_token_len_per_gpu` assert failure**: a single sample's
   stitched length exceeds `ppo_max_token_len_per_gpu` →
   `verl/verl/utils/seqlen_balancing.py:384` raises
   `AssertionError("max_token_len must be greater than the sequence length")`.
   This fires BEFORE OOM and is the most common stitched-path failure.
3. **Throughput collapse with no OOM**: `use_dynamic_bsz` packs
   1 sample per micro-batch (because each is huge), step time goes
   from minutes to tens of minutes. wandb shows GPU utilization fine
   but step throughput drops 5-10×.
4. **Train/eval reward gap > 10%** on OVOBench (cross-chunk attention
   leakage hypothesis — model uses information at training time it
   doesn't have at rollout/eval time).
5. **Want to train on >120-chunk trajectories** (catalog 120-240s tier
   is 32% of candidates; >240s adds another 10%).
6. **Actor OOM** despite `use_dynamic_bsz=True` and offload — last
   resort signal, by this point you've already hit (1)/(2)/(3).

**Not trigger** (don't do v12.14 prematurely):
- Multi-Q baseline at 60-120 chunk trajectories shows reward learning
- Eval acc improves in lockstep with train reward
- No tail truncation observed in rollout logs

## Risks not addressed by v12.14

- **D1 recall multi-turn within an action** still has its own attention
  scope (turn1 + tool_response + turn2 attend to each other). This is
  CORRECT — they're one logical step. But it means each action's max
  prompt budget needs headroom for ~3-7K of tool-response frames.
- **GRPO group size**: `n=8` rollouts × 360 actions × N trajectories =
  thousands of training samples per step. ppo_mini_batch_size needs
  re-tuning. ReMemR1 uses larger `mini_bs=512` for this reason.
- **Sample-index bookkeeping** introduces one more thing to break in
  pyarrow round-trips. Defensive `_safe_list` style coercion needed in
  the recurrent batch path.
