## What's NOT done — the actual ray_trainer integration

### Why this needs its own PR

verl 0.4 uses `AgentLoopManager` (verl/verl/experimental/agent_loop/),
where `AgentLoopBase.run()` returns **one stitched `AgentLoopOutput`**
per input row. ReMemR1 uses `AsyncLLMGenerationManager` (separate
class), where `Agent.rollout()` returns **N independent conversations**
(this PR's `AsyncStreamingVideoAgent.rollout()` matches that contract).

These are two different RL frameworks. Integrating v12.14 into verl 0.4
specifically requires bridging them. Three approaches:

#### Option A — fork-and-modify verl 0.4 (ReMemR1 style)
Vendor ReMemR1's modifications to `ray_trainer.py` (~150 lines of
if/else inside `fit()`'s main loop) + add `recurrent.enable` config
schema. Use ReMemR1's `AsyncLLMGenerationManager` directly, bypassing
verl's `AgentLoopManager` entirely.

- Pros: tested in production by ReMemR1
- Cons: large diff against vendored verl; conflicts on every verl
  upstream sync; bypasses verl 0.4's agent_loop framework which means
  losing prefix cache / mm cache / chunked prefill optimisations
- Estimate: ~2 days

#### Option B — extend `AgentLoopBase.run()` to return `List[AgentLoopOutput]`
Make verl 0.4's agent_loop framework natively support N actions per
input row. `AgentLoopWorker.handle_request` collects N outputs;
`AgentLoopManager.generate_sequences` flattens to `len(input) * N`
DataProto rows; ray_trainer's `fit()` learns to handle the inflated
batch size.

- Pros: keeps verl 0.4's optimisations; smaller change surface than
  Option A; clean conceptual fit (N-action is what `n=k` already does
  for GRPO group, just at the trajectory level)
- Cons: changes verl's agent_loop API (will conflict with upstream
  unless contributed back); requires touching downstream consumers of
  `AgentLoopOutput`
- Estimate: ~3-5 days

#### Option C — hybrid: stitched rollout, tagged with action boundaries
Keep `AgentLoopOutput` 1-output-per-row, but add a
`chunk_boundaries: List[int]` metadata field marking action spans.
Actor side uses these for block-diagonal attention (D2 — also deferred).
Reward stays per-trajectory.

- Pros: smallest verl-side change; doesn't break the 1-input-1-output
  contract
- Cons: doesn't actually solve the OOM ceiling (each row is still a
  single 50K-token stitched sample); only solves train/eval drift
- Estimate: ~1 day for boundaries, ~2 weeks for D2 attention kernel

### Recommended

**Option B** is the right answer technically, but only worth doing
when stitched (current default) trajectories on real production data
hit one of the audit-listed failure modes (truncation / max_token
assert / throughput collapse / >120 chunk needs / actor OOM). Until
then v12.14's rollout reference + smoke is enough to prove the
direction works; the stitched path with MAX_TURNS=120 covers the
batch1+lower batch2 range (60-180 chunks).

## Next steps when v12.14 is activated

1. **Decide Option A vs B** based on whether to invest in upstreaming
   to verl 0.4 (B) or stay in fork (A).
2. **Implement chosen option** + wire `recurrent.enable=memory` config
   flag end-to-end.
3. **Real vLLM smoke**: regenerate parquet with multi-Q + run a
   single-trajectory training step, verify per-action loss / advantage
   computation matches expectations.
4. **Compare with stitched baseline** on 60-120 chunk data: reward
   curve, eval acc, step time, GPU memory.
5. **Push to >180 chunks** once baseline validates — this is where
   stitched can't compete.

## Context — when to actually trigger this work

(From `docs/v12.14_recurrent_design.md` trigger list, in firing order:)

1. Tail truncation in stitched rollout (`streaming_agent_loop.py:1140/:1348`)
2. `seqlen_balancing.py:384` `max_token_len` assert
3. Throughput collapse with no OOM
4. Train/eval reward gap > 10% on OVOBench
5. Want >120-chunk trajectories
6. Actor OOM despite `use_dynamic_bsz`

If you're not seeing 1-3 yet on the current MAX_TURNS=120 production
config, don't start v12.14 ray_trainer integration. The rollout
reference is here when you need it; the cost of premature integration
(a 3-5 day fork that complicates verl upstream sync) outweighs the
benefit until production actually demands >180-chunk trajectories.
